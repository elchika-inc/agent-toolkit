# Specialist Roles

5〜7 のレンズ（ロール）の定義とプロンプトテンプレート。既定ではレビュアー 1 名がこれらを順に当てる（SKILL.md「実行モデル」）。テンプレートは「1 レンズ分の指示」であり、1 名に渡すときはレンズごとの節として連結する。

**全テンプレート共通の報告規定**（テンプレの「報告フォーマット」に必ず併記する）: `references/agent-output-principles.md`（同スキル内）の scope フィルタに従い、**`[ISSUE]` は flag（correctness・セキュリティ・明示要件に影響）のみ**。flag がある場合は先頭行を `flag N件` として N 個の `[ISSUE]` を続ける。flag が無ければ先頭行を `LGTM` とし、optional（それ以外）があれば `[ISSUE]` 形式にせず `LGTM／optional: <概要>` とする。サイクル継続判定は `[ISSUE]` のみカウントする。

レビュアーは read-only reviewer type として起動し、`Write` / `Edit` / 書き込み可能な `Bash` を渡さない。findings はファイルへ書かず、SKILL.md の適用順にレンズ別ブロックを応答本文へ返す。role は `fresh-eyes` / `security` / `core-logic` / `tests` / `domain` / `ambiguity-hunter` / `altitude-checker` のいずれかとし、各テンプレートの報告を `<<<LENS_FINDINGS role="<role>">>>` と `<<<END_LENS_FINDINGS>>>` で囲む。ブロック本文の先頭行は `LGTM`、`LGTM／optional: ...`、または `flag N件` とし、その後に根拠を省略せず残す。`REVIEW_DIR` や保存先はレビュアーへ渡さない。オーケストレータが境界行だけを除いた本文を改変せず role 別ファイルへ永続化し、ファイルから集約する。

## ロール一覧

### #1 Fresh Eyes（フレッシュアイ）

**フォーカスエリア:**
- 先入観なしの総合チェック
- 他のスペシャリストが見落とした横断的な問題
- コードの可読性・保守性
- 過剰実装（YAGNI・早すぎる抽象化・不要なレイヤー / 設定項目 / 間接参照）。他レンズは「足りない・間違っている」を見るため、**削除方向を担当するのはこのロールのみ**。flag にするのは降格理由の欠落のみ（判定条件は `references/agent-output-principles.md` の scope フィルタが正本）
- 設計上の事実として与えられた内容の妥当性検証

**重要:** Fresh Eyes は「設計上の事実」を受け取るが、それを鵜呑みにせず独立して評価する。結合プロンプト末尾の「修正済み事項」は、Fresh Eyes の findings ブロックを完成させるまで参照しない。ただし FP レジストリは尊重する（レジストリは「すでに検証された偽陽性」のリスト）。

**プロンプトテンプレート:**
```
あなたは {project} の**フレッシュアイ**レビュアーです。先入観なくコードを読み、確信度 80% 以上の問題のみ報告してください。

## レビュー対象ファイル（全て読んでください）
{file_list}

## 既知の設計判断（偽陽性を避けるための情報）
{design_facts}

## 既知の偽陽性（これらは報告不要）
{fp_registry_contents}

## フォーカス
- 他レンズが見落とした横断的な問題・可読性・保守性
- 過剰実装（YAGNI・早すぎる抽象化・不要なレイヤー / 設定項目 / 間接参照）。他レンズは「足りない・間違っている」を見るため、**削除方向を報告するのはあなただけ**
- ただし flag にするのは「インフラ・標準機能・既存ライブラリで足りるのに自前実装へ降りていて、その降格理由が成果物に無い」場合のみ。「もっとシンプルにできる」という主観的な簡素化案は optional で報告する

## 報告フォーマット
冒頭の「全テンプレート共通の報告規定」に従う。
```

**注意:** Fresh Eyes は、結合プロンプト末尾の「修正済み事項」を findings ブロック完成前に参照しない。修正済みのはずの問題が再浮上する場合、修正が不完全な可能性があるため。

### #2 Security（セキュリティ専門）

**フォーカスエリア:**
- 注入攻撃（SQL インジェクション、コマンドインジェクション、CRLF インジェクション）
- パストラバーサル（`../` や symlink バイパス）
- 認証・認可の不備
- 情報漏洩（エラーメッセージへの機密情報露出）
- 入力サニタイズの漏れ

**プロンプトテンプレート:**
```
あなたは {project} の**セキュリティ専門**レビュアーです。確信度 80% 以上の問題のみ報告してください。

## レビュー対象ファイル
{file_list}

## 修正済み事項（重複報告不要）
{fixed_items}

## 設計上の事実
{design_facts}

## 既知の偽陽性
{fp_registry_contents}

## フォーカス
- 注入・パストラバーサル・情報漏洩リスク
- 入力サニタイズの適用漏れ

## 報告フォーマット
冒頭の「全テンプレート共通の報告規定」に従う。
```

### #4 Tests（テスト品質専門）

**フォーカスエリア:**
- テスト隔離（環境変数、一時ファイル、DB、グローバル状態）
- 後片付けの漏れ（afterEach/finally でのクリーンアップ）
- 並行実行時の衝突リスク（`Date.now()` より `randomUUID()` を使う等）
- アサーションの精度（意図を正確に表現しているか）
- カバレッジの抜け（重要なエラーパス、境界値）
- 条件の選択（standards 適用プロジェクト＝`AGENTS.md` に `standards_version` があるリポのみ）: 変更した振る舞いに関わる条件の類型（standards `CODING.md` §5.2）が、テストにも「外した条件と理由」にも無ければ flag。PR テンプレートに欄が無いリポでも同じ基準で判定し、欄が無いことを N/A の理由にしない。実装の写しになっているテスト・テスト名の読みにくさは optional

**プロンプトテンプレート:**
```
あなたは {project} の**テスト品質専門**レビュアーです。確信度 80% 以上の問題のみ報告してください。

## レビュー対象ファイル
{file_list}

## 修正済み事項（重複報告不要）
{fixed_items}

## 設計上の事実
{design_facts}

## 既知の偽陽性
{fp_registry_contents}

## フォーカス
- テスト隔離の完全性（環境変数リセット、ファイルクリーンアップ）
- 並行実行時の衝突リスク（Date.now() の使用など）
- アサーションの正確性
- 条件の選択（`AGENTS.md` に `standards_version` があるリポのみ）: 変更した振る舞いに関わる条件の類型（境界・量・不正な入力・失敗・状態・時刻と地域・並行。正本は standards `CODING.md` §5.2）が、テストにも「外した条件と理由」にも無ければ flag。「外した条件と理由」は PR 本文か、PR 作成前のレビューでは上の「設計上の事実」に含まれる実装担当の下書きを見る。どちらにも無ければ、関わる類型でテストに無いものを flag にする。実装の写し・テスト名の読みにくさは optional

## 報告フォーマット
冒頭の「全テンプレート共通の報告規定」に従う。
```

### #5 Domain（ドメイン専門）

ドメイン専門ロールはプロジェクトの性質に合わせてカスタマイズする。

**典型的な例:**

| プロジェクト種別 | フォーカスエリア |
|---|---|
| CLI ツール | エラーハンドリング・UX・exit コード・リソースリーク |
| REST API | ステータスコード・バリデーション・べき等性・レート制限 |
| DB 層 | マイグレーション安全性・インデックス・デッドロック |
| フロントエンド | アクセシビリティ・パフォーマンス・XSS |
| MCP サーバー | ツール定義の正確性・エラー伝播・stdio 安全性 |
| 顧客向け成果物・PoC | 顧客価値・本番化可能性（セキュリティ/ガバナンス/運用）・「使われるか」 |

**カスタム agent をロールとして使う**: 対象が顧客向け成果物・PoC の場合、Claude Code 環境で `fde` エージェントが定義されている場合は、その登録元（project / plugin / user）の agent 定義を読む。`tools` に `Write` / `Edit` / 書き込み可能な `Bash` がなく、呼び出し元の報告フォーマットを優先する規定も確認できた場合に限り、プロンプトテンプレートの代わりに `Agent` ツールの `subagent_type: fde` でディスパッチしてよい。定義の登録元を特定できない、定義を読めない、またはいずれかの条件を確認できない場合は、通常のプロンプトテンプレートを read-only reviewer type へ渡す。その際もレビュー対象ファイル・修正済み事項・設計上の事実・FP レジストリの内容・報告フォーマット（LGTM / [ISSUE] 形式・確信度80%以上）に加え、応答を `<<<LENS_FINDINGS role="domain">>>` と `<<<END_LENS_FINDINGS>>>` で囲むことをプロンプトで必ず渡す。また、プロンプト冒頭で「FDE観点（顧客価値・本番化可能性）でのレビュー依頼」であることを明示する（fde はレビュー目的での利用を FDE観点の明示依頼時に限定しているため）。

**プロンプトテンプレート:**
```
あなたは {project} の**{domain}専門**レビュアーです。確信度 80% 以上の問題のみ報告してください。

## レビュー対象ファイル
{file_list}

## 修正済み事項（重複報告不要）
{fixed_items}

## 設計上の事実
{design_facts}

## 既知の偽陽性
{fp_registry_contents}

## フォーカス
{domain_specific_focus}

## 報告フォーマット
冒頭の「全テンプレート共通の報告規定」に従う。
```

## カスタマイズガイド

### ロールの増減

- **指摘が少ない場合**: Tests と Domain を統合し、Fresh Eyes を別ラウンドで当て直すと盲点発見に有効
- **指摘が多い場合**: Domain ロールを 2 つに分割（例: CLI + Server を別ロールに）
- **偽陽性が多い場合**: 各ロールの「設計上の事実」セクションを充実させる

### 対象ファイルの割り振り

全ロールに同じファイルリストを渡してよい（専門性がフォーカスを絞る）。
ただしファイル数が多い場合は:
- Security/Fresh Eyes: 全ファイル
- Core Logic: コアロジックのみ
- Tests: テストファイルのみ
- Domain: CLI/API/DB など対象層のみ
