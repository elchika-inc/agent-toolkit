# Delegation Spec — 委任仕様テンプレ

司令塔が worker（Codex / Claude）へ渡す task spec の必須構成。worker は literal に実行し、曖昧さを意図で補完しない前提で書く。

## 必須7節

1. **背景** — 前提事実と実測済み事項。worker に再調査させない範囲を明示する
2. **実施内容（literal）** — ファイルパス・変更単位まで具体化。「〜の趣旨で」を使う場合は範囲を限定する。数値・時間オプションは単位・境界値・不正値の扱いまで書く（下記）
3. **スコープ外** — 触ってはいけないファイル・やってはいけない操作を列挙する
4. **検証（rubric）** — 下記チェックリストを満たすこと。結果は worker_done の body に実測値で含めさせる
5. **レビューサイクル** — 実施者（委譲先で完結）を明記。レンズ選定は brain `ref-work-archetypes-bcherny` の対応表、収束規律は standards `AI_FIRST.md` §3 の値で（スキル既定値を上書き）。**最大ラウンド数を明記する**（下記）。**レビューの実行手段も書く**（下記）
6. **完了条件** — PR 作成まで。main へのマージは human-gate。PR 本文の要件（変更概要・検証結果・レビュー記録・実装担当識別子）。既存の PR・文書へ積む委任では、**既存本文の扱い**も書く（下記）
7. **制約** — 「指示と実態が矛盾したら止めて ask で報告」（MUST）＋裁量範囲と変更申告義務。**逆委任は受けない**——環境制約（thread / turn 上限・ツール不在等）で担当範囲を遂行できないときは、司令塔へ範囲を戻さず ask で報告して判断を待つ。事前合意済みの代行に別作業を同梱しない（司令塔側の規律は `~/.claude/CLAUDE.md`「エージェント役割分担」）

## 検証節の事前チェックリスト（書く前に司令塔が確認する）

失敗パターンの正本は `~/.claude/references/verification-pitfalls.md`。

- [ ] 検証コマンドは**書く前に実行してベースラインを取った**か（「PASS するはず」を期待値にしない）
- [ ] probe に使う値（クラス名・文字列・パス）の**実在を確認した**か
- [ ] 負の検査（禁止語 0 件等）は**出現位置まで指定した**か（部分文字列の偽陽性——実例:「ッピ」probe が「マッピング」に命中）。さらにその probe を**仕様に書いた置換後文言そのものに対して実行し 0 件**を確認したか（実例: 置換後文言に訂正履歴として置換前の語を引用したため、同じ語の負の検査が置換後に必ず命中した）
- [ ] 検証コマンドに pipe・`&&` 連結・`|| true` を**含めていない**か（個々の exit code を確認する形か）
- [ ] 検証コマンドを**表のセルに書いていない**か。Markdown のセル内 `|` はエスケープが要り、`grep -E 'A\|B'` の `\|` は ERE では**リテラルのパイプ**になって交替として解釈されず、意図した候補群にマッチせず、「0 件＝準拠」の偽の通過を作る（実例: 中立性検査の probe が沈黙し、worker も司令塔も気づけなかった）。コマンドは**コードフェンスに置き、表からは参照する** → brain `URISK-116`
- [ ] 背景に、**worker が着手時に自分で観測できる事実**（ブランチ名・作業ツリーが clean か・ファイルの行数・依存やディレクトリの有無）を書いていないか。司令塔は main checkout で測るため、worktree とは別ディレクトリ・別ブランチ・別ファイル集合になり、書けば食い違って `ask` の往復を生む（実例: 1 セッションで 4 回の ask のうち 3 回がこれ）。背景に書くのは**観測しにくい事実**（設計の意図・過去の裁定とその理由・別リポの規定・ライブラリの内部実装・ベースラインの実測値）に限り、観測できる事実は rubric に**測る手順**として置く
- [ ] 検証報告に**実測の範囲**（可視 / 存在 / 実行 / 動作のどこまで測ったか）を要求したか
- [ ] 独立検証は**情報源まで分けた**か（間接証拠でなく実体への直接照会を1本混ぜる——実例: ディレクトリ一覧で「未配布」と誤判定、ランタイム照会で覆った）
- [ ] worker の完了判定は worker_done の受領でなく**成果物の実体との突合**にしたか
- [ ] 挿入・置換の**位置指定は基準語を 1 つ**にしたか（「X の直前」と「Y の後ろ」を併記すると、どちらに係るか worker が読めない——実例:「`…Rev3…)` の直前」と括弧内の「Rev3 の後ろ」の併記で ask が発生）
- [ ] 仕様本文に**司令塔側のチャット規律**（語尾の指定など）を書いていないか。仕様を成果物（plan ファイル）として保存させると、禁止文字列を含む仕様自身が規律に違反する（実例: 語尾の禁止行を含む仕様を `.docs/plans/` へそのまま保存させて ask が発生）
- [ ] レビュアーに課す制約（ツールを渡さない等）を、**委譲先の harness で実現できる手段まで**書いたか。スキルが要求する制約と、worker を起動した harness が表現できる引数は一致しないことがある
- [ ] 既存の PR・文書へ積む委任で、**既存本文のどの節を置換し・どの節へ追記し・どの節を維持するか**を書いたか

## レビューの実行手段まで書く

レビューの規律（レビュアーの人数・レンズ・ツール制限）を定めるのはスキルだが、それを**実行できるかは worker を起動した harness が決める**。スキルの要求と harness の表現力が食い違うと、worker は自分で埋めてよいか判断できず止まる。仕様には「誰が・どのレンズを・何ラウンド」に加えて、**その制約を満たす実行手段**（どのコマンド・どのコンテキストで走らせるか、記録をどこへ残すか）を書く。委譲先の harness に手段が無いなら、司令塔が先に代替手段を決めて仕様へ書く。

**実例**: `lens-review-cycle` はレビュアーへ書き込みツールを渡さないことを求めたが、worker を起動した Orca の `worker-start` にはレビュアーのツールを制限する引数がなく、3 worker 中 2 名が独立に同じ ask を出した。司令塔は、別コンテキストの `claude -p` にツールを渡さず、差分と対象全文を stdin で渡してレビューする方式を裁定した。**レビューの規律はスキルが決めるが、実行可能性は harness が決める。**

## 既存の成果物へ積む委任は、既存本文の扱いを書く

未マージ PR のブランチや既存の文書へ追加コミットを積む委任では、**既存本文が今回の変更と矛盾しうる**。「追記する」とだけ書くと、worker は矛盾を残すか、勝手に書き換えるか、止まって聞くかの三択になる。節ごとに **置換 / 追記 / 維持** のどれかを指定する。目安は、変更後の状態を説明する節（PR の変更概要など）は矛盾箇所を最小置換、履歴として積み上がる節（検証結果・レビュー記録）は既存を残して末尾へ追記、司令塔や他者が書いた節は維持。

**実例**: 未マージ PR へ追加コミットを積む委任で「PR 本文の変更概要に 1〜2 行追記する」とだけ指定したところ、worker は今回の変更と矛盾する旧記述を 3 箇所見つけ、追記だけでは矛盾が残ると ask した。司令塔は「矛盾箇所は最小置換、他節は維持」と裁定した。**PR 本文の変更概要は変更の履歴ではなく、マージ後に残る最終状態の説明である。**

## レビューサイクルの上限をタスクごとに決める

**最大ラウンド数を委任仕様に明記する。** 書かなければスキル既定値（`lens-review-cycle` が正本）が使われ、
タスクの規模に対して過大／過小なことがある。

- 仕様が確定していて範囲が限定的（数ファイルの修正・ドキュメント整合） → **2〜3 ラウンド**
- 新機能・設計変更を含む → **5 ラウンド程度**
- 上限に達しても flag が残る場合は、打ち切って現状を報告させる（自律実行原則の例外）

**実例**: 仕様が確定した中規模タスク（MCP の診断改善＋設定生成）で上限を書かずに委任した結果、
既定のまま 9 ラウンド・4 時間走り、テストが 200→304 件に増えた。成果物自体は健全だったが、
上限を書いていれば同じ品質へ短時間で到達できた。**上限の指定は品質でなく所要時間を決める。**

## 数値・時間オプションは単位・境界・不正値まで書く

`--timeout <sec>` のように名前と単位だけ書くと、0・負数・小数・上限・丸め方法の扱いが未定義のまま実装へ渡り、
レビューで同じ領域が繰り返し指摘される。仕様に書くのは次の 4 点。

- **単位**（秒かミリ秒か。内部で変換するなら丸め方法も）
- **境界値**（下限・上限。ランタイム固有の上限があるならその値）
- **不正値の扱い**（0・負数・非数を受けたときエラーか既定値か）
- **適用範囲**（そのオプションがどのコマンド・どの通信に効くか）

**実例**: 配送表現の導入タスクで「CLI に `--timeout <sec>` を追加する」とだけ書いた結果、
レビュー R2〜R5 の 4 ラウンドが timeout の境界だけに費やされた
（境界値 → Node timer の実効上限 → 丸め前の入力境界 → 秒からミリ秒への変換で生じる浮動小数点誤差）。
同じ委任の他項目（型の shape・アドレス規則・除外するフィールド）は literal に書いたため 1 ラウンドで収束している。
**レビューのラウンド数は実装の難しさではなく仕様の解像度を映す。**

## 所要時間の目安を渡し、無進捗の判定基準を決めておく

**ラウンド数の上限だけでは「遅い」の基準にならない。** 司令塔は待つ側なので、目安が無いと沈黙を異常と誤認して不要な割り込みをかける。委任時に次を伝える。

- **想定所要時間**（例: このタスクは 30〜60 分。その間 commit が無くても正常）
- **無進捗と判断する基準**（何を、どれだけ観測できなかったら確認するか）

司令塔側の観測は **commit と PR の有無**を基本にする。ファイル更新時刻のような細かい観測はクエリを誤ると偽の異常を生む（→ brain `risk-negative-result-unverified-query`）。amend を使う worker もいるので、commit は件数ではなく**ハッシュの同一性**で見る。

**実例**: 大規模な撤去タスク（21 ファイル）で時間の目安を渡さずに委任した結果、「10 分 commit が無い」を異常と誤認し、正常に作業していた worker を割り込みで停止させた。実際には未コミットのまま数分おきにファイルが更新されており、レビュー往復中だった。**中断のコストは実作業より、司令塔と worker の双方が状況説明に費やす往復のほうが大きい。**

## 追い送りは元仕様のどこを上書きするか名指しする

dispatch 後に司令塔が送る追加指示（先回りの裁定・方針変更）は、**元仕様と同じ重みで literal に読まれる**。どの節を上書きするのか・補足なのかを書かないと、worker は元仕様と新しい指示の競合として検出し、止まって聞く。追い送りには「元仕様 §N の〈該当文〉を〈新しい文〉に置き換える」「元仕様 §N はそのままで、これは追加の条件」のどちらかを明記する。短い指示ほど、元仕様のどこに当たるかを書き落としやすい。

**実例**: 司令塔が先回りの裁定として「レビュー記録の節は触らない」と追い送りしたところ、元仕様 §5 の「残った指摘はレビュー記録に追記する」と競合し、worker が ask で止まった。司令塔は、既存記述の書き換えを避ける意図だったと説明し、「既存記述は維持し、末尾に今回分を小見出し付きで追記」と訂正した。**追い送りは元仕様の差分であり、差分は適用先を指して初めて適用できる。**

## 委任開始時の司令塔側手順

1. rubric を `/goal` へ積む文面をユーザーに提案する（CLAUDE.md「完了ゲート」の既定）
2. dispatch 後は送信を到達と見なさず、**worker が動いていることを実測**してから待機に入る（terminal 出力・作業ツリーの実体）
3. worker_done 受領後、**ack する前に**完了ゲート（rubric 突合・負の検査・スコープ確認）を独立実施する
