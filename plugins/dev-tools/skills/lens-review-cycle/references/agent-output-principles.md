# エージェント出力原則

レビュー系エージェント（pr-review-toolkit など）を起動する際の出力方針。

## 確信度ベースのフィルタリング
- 確信度 80% 以上の指摘のみ報告する。量より質。
- レビュー（問題の発見）と修正（変更の実装）を分離する。1つのエージェントに混在させない。

## scope フィルタ（flag / optional の分離）
- flag（要対応）にできるのは **correctness・セキュリティ（脆弱性・秘密漏えい・データ破壊）・明示要件に影響する指摘のみ**。それ以外（スタイル・過剰な防御・起き得ないケースへの備え）は **optional** として分離して報告する。
- correctness はコードの正しさに限らない。**文章仕様（ルール・spec・CLAUDE.md 等）のレビューでは、従うと誤実装・誤運用・収束不能に至る欠陥**（矛盾する定義・二義的な境界・収束条件の欠落・anti-gaming 穴・宙吊り参照）**を correctness 相当として flag** する。表現の好み・冗長さは optional。
- flag には**失敗の示し方**を添える——どの入力・状態で何が誤った結果になるか（文章仕様なら、その記述に従うと何を誤実装・誤運用するか）。lens-review-cycle の `[AMBIGUITY]` / `[ALTITUDE]` は `問題:` 行が示し方を兼ねる。
- **過剰実装は既定 optional**（上記の「過剰な防御・起き得ないケースへの備え」に含む）。ただし「インフラ・標準機能・既存ライブラリで足りるのに自前実装へ降りていて、**その降格理由が成果物に残っていない**」場合のみ **correctness 相当として flag** する——検証できない判断が残っている状態を指摘するのであり、「もっとシンプルにできる」という主観的な簡素化案とは別物（主観を flag にすると収束しない。理由は下記根拠と同じ）。
- 根拠: 粗探しを指示されたレビュアーは健全な対象にも指摘を出すため、全指摘追従は過剰設計に至る（brain `ref-claude-md-harness-2026`）。
- optional はレビューサイクルの終了条件に数えない（修正・明示受容とも不要）。ただし記録はディスクに残す——コード変更なら `INSPECTION_STATUS` に `optional N件: <一言概要>` を併記、それ以外はレビュー成果物（PR コメント・`.docs/plans/` 等）へ、いずれも無い場合（リポ外・グローバル設定等）はレビュー対象ルート直下の `.docs/reviews/YYYY-MM-DD-<対象>.md` に残す。チャット出力のみは記録と見なさない。絞るのは入口＝レビュアーへの指示であり、flag された指摘の格下げ（anti-gaming 違反）ではない。

## 誤検知の除外
以下は実問題ではない。指摘しない。**ただし優先規則: 値が実鍵形式（`sk_live_`・`AKIA`・`ghp_`・PEM 秘密鍵ブロック等）にマッチする場合は下記の全項目に優先して flag する**——除外できる根拠は `ACCEPTED_RISKS` 等ディスク上の明示受容記録のみ（コメント・置き場所・変数名などの自己申告は根拠にしない）。
- `.env.example` のダミー値
- テストファイル内のダミー形式の認証情報
- 公開前提の credential 形式のキー（`pk_` 等）。`NEXT_PUBLIC_` 等の変数命名は、値が実鍵形式でない場合のみ除外根拠になる
- チェックサム用途の SHA256 / MD5（パスワードハッシュではない）
- 今回の変更と無関係な既存の問題
- リンター・型チェッカー・CI が検出する問題
