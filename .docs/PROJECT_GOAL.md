# PROJECT_GOAL — agent-toolkit（ゴールシート）

## 位置づけ（Outcome）

- **誰のために**: 開発エージェントを利用する開発者と、スキル・プラグインの保守担当者。
- **どんな問題**: リポジトリごとにレビュー・検証・運用の道具を作ると、手順と配布内容が分岐して保守が重くなる。
- **どう解く**: 共通スキルとプラグインを一箇所で保守し、利用者は対応する CLI からインストール・更新する。
- **なぜ agent-toolkit か**: standards が持つルールと、それを実行する道具の正本を分け、複数のエージェントへ同じ道具を配布できる。

## 原則（Constraints）

| ID | 原則 | 反例 |
|---|---|---|
| P-1 | ルールの正本は standards、実行する道具の正本はこのリポジトリに置く | standards の検査項目をスキルへ複製し、改訂に追従できなくする |
| P-2 | エージェント横断のスキルは共通の正本から配布する | 配布先だけを編集してリポジトリと内容が分岐する |
| P-3 | 公開した配布識別子と利用契約の互換性を保つ。破壊的変更は版を上げ、移行手順を残す | マーケットプレース名を無断で変え、既存インストールを孤立させる |

### 適用範囲

P-1 は standards と道具の責務分担、P-2 は `skills/` とその同期コピー、P-3 はスキル・プラグイン・MCP ツールの公開面に適用する。エージェント固有の機能は `plugins/` に置けるが、横断スキルの正本は `skills/` に保つ。

## 能力（Scope）

面: スキル、プラグイン、ローカル MCP。形の正本は [skills/](../skills/)、[プラグイン配布定義](../.claude-plugin/marketplace.json)、[MCP サーバー](../plugins/elchika-tools/mcp-server/) に置く。

| ID | 能力 | 面 | 根拠 |
|---|---|---|---|
| C-001 | 利用者がレビュー・検証・設計・運用の共通スキルをインストールし更新できる | スキル / skills CLI | [README の Skills](../README.md#skills) |
| C-002 | 利用者が agents・commands・hooks と同期スキルをプラグインとして利用できる | プラグイン | [dev-tools](../plugins/dev-tools/)、[開発プロセスの設計](plans/dev-process-plugin-design.md) |
| C-003 | 利用者が変換・生成などのユーティリティをローカルで呼び出せる | MCP | [MCP サーバー](../plugins/elchika-tools/mcp-server/) |

## やらないこと（OutOfScope）

| ID | やらないこと | 反する原則 |
|---|---|---|
| N-001 | standards と独立した共通ルール集を配布物内に複製して維持する | P-1 |
| N-002 | インストール先をスキルの正本として保守する | P-2 |
| N-003 | 配布識別子や利用契約を移行手順なしに破壊する | P-3 |

## SuccessCriteria

### ローンチ判定

| 基準 | 確認方法 | 備考（達成状況） |
|---|---|---|
| 共通契約と利用手順を配布物の正本からたどれる | [AGENTS.md](../AGENTS.md) と [README](../README.md) の実在・リンク・コマンドを照合する | 本シートで状況を管理し、変更 PR に検証結果を記録する |
| スキル・プラグインの変更が利用者の配布先へ届く | AGENTS.md「重要な設計原則」の更新手順後に、配布先の実ファイルを変更内容と照合する | 未設定（変更担当者が配布確認時にこの表と変更 PR へ結果を記録する） |
| MCP の既存動作を保つ | `npm --prefix plugins/elchika-tools/mcp-server test` を実行し、結果と exit code を確認する | 2026-09-10: 1ファイル・34テスト成功、exit 0。実行ログは本変更の PR に記録する |

### プロダクトの成功

| 基準 | 確認方法 | 備考（達成状況） |
|---|---|---|
| 未設定（保守担当者が利用者の導入・更新時の負担を基に、このシートの改訂 PR で目標を決める） | 未設定（保守担当者が同じ改訂 PR で導入・更新の成否などの測定方法を決める） | 数値目標は未設定。配布ファイルの存在だけで利用成功とは判定しない |

## DoneCriteria

[standards AI_FIRST §3](https://github.com/elchika-inc/standards/blob/main/AI_FIRST.md#3-ai-レビューサイクルmust) の既定に従い、変更ごとに次を満たす。

- レビューサイクルで確信度80%以上の flag を修正または明示受容し、ラウンド数・指摘件数・判断を PR に記録する。受容する欠陥は [リスクレコード](risk-registry.md) へ anchor とともに記録する。
- AGENTS.md の Key Commands の test と check をコマンド単位で実行して exit 0 を確認する。N/A は同節に理由が明記されている項目だけに適用する。
- ドキュメント変更は実ファイルの記載・リンク先・正本との整合を確認し、存在確認と実行検証を区別した証跡を PR に残す。
- `skills/` を変更したら、AGENTS.md「skills/ 変更時」に従って配布先の実体で反映を確認する。
- `plugins/` の中身を変えたら、該当プラグインの `plugin.json` と `marketplace.json` の version を同じコミットで同じ値へ上げる。
- AGENTS.md「整合性の維持対象」を満たし、PR を作成して実装担当識別子を一貫して記録する。マージは `merge_policy: human` に従い、人間の承認を経る。

## 判定手順（Issue 起票時）

1. この変更はどの C-### を実現・改善するか。無ければ 2 へ。
2. どの N-### にも当たらないか。当たるならこのシートの改訂 PR が先。
3. どの P-# にも反しないか。反するならこのシートの改訂 PR が先。

新しい能力は Issue に `NEW` と書き、このシートの改訂 PR を先に出してから実装に入る。

## 改訂手順

- 原則・能力・やらないことの追加と退役は、このシートを変更する PR で行う。ID は欠番を再利用しない。
- 退役は行を消さず `(retired: YYYY-MM-DD 理由)` を付けて残す。
- 見出し文字列は変えない。変えるときは実在する参照元（[AGENTS.md](../AGENTS.md) と [レビュードキュメント](reviews/)）を同じ PR で直す。
- 改訂 PR のマージが判断の出来事。経緯は [plans/](plans/) の設計ドキュメントか [reviews/](reviews/) のレビュードキュメントに残し、PR 本文からそれを指す。
- 空欄を置かない。未確定は「未設定（誰が・どこで決める）」と書く。
